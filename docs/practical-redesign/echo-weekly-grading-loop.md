## Risk evidence envelope (applies NOW, both models)

Every practical decision is submitted through `echo_client.py submit` as an envelope `{requestId, leaseToken, decision, riskEvidence}`. `riskEvidence` is required for practicals (never for quizzes). It must have **exactly** these keys, or the server answers `RISK_EVIDENCE_REQUIRED_PENDING`:

**`noPlan` alternative (DAILY_LOG_V1, after Platform deploys PR #14; decided 2026-11-19; names as in PR #14, head `e402081`):** for M1–M5, A6 and A7 only, when the Friday file has no Final Paper Plan **and the packet shows `tradeDays` 0**, submit `{requestId, leaseToken, decision, noPlan: true, noPlanReason}` **instead of** `riskEvidence` (exactly one of the two; `riskEvidence` with `noPlan` is `PLAN_AND_NO_PLAN_CONFLICT`, `noPlan` without a 20–500 character reason is `NO_PLAN_REASON_REQUIRED`, `noPlan` with `finalHardBlock:true` is `FINAL_HARD_BLOCK_MISMATCH`). `noPlanReason` states why there is no plan and what grounds the no-trade days, with entry IDs and timestamps. The routine gate and the verdict rule apply as usual. On A8 (`weekPlanRequired: true`, `planPolicy: required`) the server rejects `noPlan` with `PLAN_REQUIRED_FOR_WEEK`: do not retry; use the A8 `reasonCode:"PLAN_MISSING_REMEDIAL"` path (Week 8 bullet above). With any recorded trade the server rejects `noPlan` with `NO_PLAN_REQUIRES_ZERO_TRADES`, and the decision carries `riskEvidence`: from the Friday plan if there is one. **For a week with trades but no Friday plan, which trade `riskEvidence` describes is a PENDING owner/Platform question; do not guess, hold the request pending and report it.** (Working proposal, unconfirmed: the worst trade entry, with every trade's `daily:<entryId>` in `evidenceRefs`; `practical-redesign/contract-changes.md` §3A.) Check `weekPlanRequired` and the per-day block in the packet first. In the LEGACY model there is no `noPlan` path.
- `currentEquity`: decimal **string**, current paper equity of the Final Paper Plan (> 0)
- `riskAmount`: decimal **string**, the plan's risk in account currency, at most 1% of `currentEquity` for a pass (> 0)
- `netReward`: decimal **string**, reward after spread/costs, same currency (≥ 0)
- `stopType`: one of `STRUCTURAL_HARD` | `MENTAL` | `NONE`
- `evidenceRefs`: array of 1–20 strings (each 1–300 chars) pointing at the original evidence, e.g. `<submissionId>:document:p1:task1`; for DAILY_LOG_V1 also `daily:<entryId>` and `daily:<entryId>:file:<fileId>`

The server derives `finalHardBlock` from it: it is true if `stopType` is not `STRUCTURAL_HARD`, or `riskAmount × 100 > currentEquity`, or `netReward < 2 × riskAmount`. Your decision's `finalHardBlock` must equal it (`FINAL_HARD_BLOCK_MISMATCH` otherwise). Values are recomputed by you from the student's evidence with exact decimals, size rounded DOWN; missing inputs mean the request stays pending (`RISK_INPUT_UNVERIFIED_PENDING`), never a guessed approval. Example from the verified kami TEST run: `{"currentEquity":"10000","riskAmount":"99.20","netReward":"220.80","stopType":"STRUCTURAL_HARD","evidenceRefs":["<submissionId>:document:p1:task1"]}`.
